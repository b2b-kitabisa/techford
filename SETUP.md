# Setup Project

Ada dua cara menjalankan project ini: pakai **clasp** (CLI resmi Google, direkomendasikan — sinkron `src/` di repo ini langsung ke Apps Script lewat command line, tanpa copy-paste manual) atau **Apps Script Editor native** (copy-paste manual, tanpa tooling lokal).

## Opsi A — clasp (Direkomendasikan)

Prasyarat: `clasp` terinstall (`npm install -g @google/clasp`) dan sudah login ke akun Google Anda (`clasp login`) — proses ini butuh Anda membuka URL otorisasi di browser sendiri, tidak bisa diotomasi penuh dari sisi manapun karena memang harus persetujuan eksplisit dari akun Google Anda.

1. Buat sheet berikut di Spreadsheet database platform ini:
   - `Employee` dengan header baris pertama: `Id | Name | Email | Role | PasswordHash | Status | CreatedAt`. Ini juga tabel login (lihat `EmployeeService.login`) — isi minimal 1 baris admin pertama secara manual (jalankan `Utils.hashPassword('passwordAnda')` sekali dari Apps Script Editor untuk dapat hash-nya, jangan simpan password polos).
   - `Lead` dengan header baris pertama: `Inbound_ID | Timestamp | Status | Entity_Name | Entity_Type | PIC_Name | Email | Phone | Detail_Interest | Priority_Notes | UTM_Source | UTM_Medium | UTM_Campaign | Last_Updated | Other_Notes`. Kolom `Status` harus berisi salah satu dari: `New Leads`, `Contacted`, `Moved`, `Other`, `Spam` (lihat `Config.LEAD_STATUS`).
   - `Inbound_Raw` — hasil `IMPORTRANGE` dari Spreadsheet respons Typeform, header (persis nama pertanyaan Typeform): `First name | Last name | Jenis organisasi | nama perusahaan/organisasi | kebutuhan | prioritas | Phone number | Email | utm_source | utm_medium | utm_campaign | Submitted At | Token`. Sel-selnya dikontrol formula `IMPORTRANGE` — jangan diedit manual.
   - `Client` dengan header baris pertama: `Client_ID | Brand_Name | Entity_Name | Entity_Type | Head_Office | Website | Industry | Client_Source | Is_From_Lead | Created_Date | Created_By | Other_Notes | Last_Updated`. `Is_From_Lead` (TRUE/FALSE) di-set otomatis SEKALI saat Client dibuat (true kalau hasil Move dari Lead, false kalau input manual) dan tidak pernah bisa diubah lagi — dipakai untuk mengunci `Client_Source` (selalu Inbound) saat client hasil Move di-edit.
   > **Kalau sheet `Client` sudah pernah Anda buat sebelumnya**: tambahkan kolom baru `Is_From_Lead`, isi `TRUE` untuk baris yang memang berasal dari Move Lead, `FALSE`/kosong untuk sisanya.
   - `PIC_Client` dengan header baris pertama: `PIC_ID | Client_ID | PIC_Name | Title | Email | Phone | Created_Date`.
   - `Master_Data` dengan header baris pertama: `Category | Value | CreatedAt`. Ini sumber opsi dropdown Head Office/Industry/Entity Type/Client Source di Client Monitoring — dikelola lewat Setting, tapi isi dulu beberapa baris awal manual, misal:
     ```
     Client_Source | Inbound   | (kosongkan/isi tanggal)
     Client_Source | Outbound  |
     Client_Source | Referral  |
     ```
     (kolom `Category` harus persis `Client_Source`, `Head_Office`, `Industry`, atau `Entity_Type`).
   - `Project` dengan header baris pertama: `Project_ID | Project_Name | Client_ID | Consultant | Services | Service_Categories | Program_Type | Program_Category | Program_Name | Issues | Other_Notes | Is_Retainer | Allow_Manual_Deal | Stage | Total_GDV | Total_Service_Revenue | Other_Document_Links | Is_Draft | Created_Date | Created_By | Last_Updated`. Ini sheet untuk modul Sales Pipeline. `Services`, `Service_Categories`, `Issues` isinya string JSON array, dan `Other_Document_Links` string JSON array berisi objek `{name, link}` (semuanya di-encode/decode otomatis oleh `ProjectService`, jangan diedit manual). `Stage` berisi salah satu dari daftar di `Config.PIPELINE_STAGE_LIST` — sengaja disederhanakan jadi cuma 4: `Prospect`, `Negotiation`, `Won`, `Loss` (progres detailnya mengikuti Document Pipeline). `Is_Retainer` (TRUE/FALSE) sengaja tidak bisa diubah lagi setelah project dibuat — ini keputusan produk, bukan bug. `Allow_Manual_Deal` (TRUE/FALSE, default FALSE) — toggle bebas yang bisa dinyala/dimatikan admin kapan saja lewat Project Detail; kalau FALSE, SELURUH dropdown Stage terkunci (termasuk Loss) dan hanya bisa bergerak otomatis lewat Document Pipeline (lihat `ProjectService.updateStage`). `Total_GDV`/`Total_Service_Revenue` dihitung otomatis (SUM) dari sheet `Revenue_Breakdown` (lihat di bawah) setiap kali Revenue Breakdown disimpan — jangan diedit manual. `Is_Draft` (TRUE/FALSE) — baris "New Pipeline" yang dibuat dari tombol "Buat Project" di Client Monitoring sebelum Consultant melengkapi lewat drawer Add Pipeline; `Project_ID`-nya SEMENTARA bukan format resmi (`PRJ26-xxxxx`) sampai dilengkapi — lihat `ProjectService.createDraftProject`/`completeDraftProject`.
   > **Kalau sheet `Project` sudah pernah Anda buat sebelumnya**: tambahkan kolom `Is_Draft` (isi `FALSE`) dan `Allow_Manual_Deal` (isi semua baris yang sudah ada dengan `FALSE`, atau kosongkan, dianggap falsy), dan perbaiki manual isi kolom `Stage` untuk baris lama yang masih pakai nilai granular (`First Approaching`/`Follow Up User` → `Prospect`; `Drafting Deck`/`Revision` → `Negotiation`; `Won`/`Loss` tetap sama).
   > **Kalau Anda sudah pernah menambahkan kolom `Gdv_Campaigns`/`Service_Revenue_Items` di sheet `Project`** (dari instruksi versi SETUP.md sebelumnya): kolom itu **sudah tidak dipakai lagi** — silakan hapus keduanya. Revenue Breakdown sekarang disimpan di sheet terpisah `Revenue_Breakdown` (lihat di bawah) supaya satu project bisa punya banyak baris breakdown sekaligus dan tetap bisa diagregasi/pivot native lewat Sheets.
   - `Revenue_Breakdown` dengan header baris pertama: `Breakdown_ID | Project_ID | Value_Type | Item_Name | Amount | Notes | Created_By | Created_Date | Last_Updated`. Satu baris = satu item breakdown revenue milik satu Project — sebuah project bisa punya banyak baris. `Value_Type` salah satu dari `Config.REVENUE_VALUE_TYPE`: `GDV` (dihasilkan dari service `CSR`, `Item_Name` = link campaign) atau `SERVICE` (dihasilkan dari service SELAIN CSR, `Item_Name` = nama category yang dipilih, atau nama service itu sendiri untuk service tanpa category seperti Ads Sponsorship/Placement & Production). `Notes` opsional, per baris. Setiap kali tombol SAVE di section Revenue Breakdown (Project Detail) diklik, SEMUA baris lama milik project itu dihapus lalu ditulis ulang dengan baris baru (lihat `ProjectService.updateRevenueBreakdown`/`RevenueBreakdownRepository.replaceForProject`) — jangan diedit manual.
   - `Document_Pipeline` dengan header baris pertama: `Doc_ID | Project_ID | Document_Type | Entity | Status | Stage | Requested_By | Requested_Date | Last_Updated`. Ini sheet untuk modul Document Pipeline. `Document_Type` salah satu dari `Config.DOCUMENT_TYPES` (DECK, QUOTATION, COR, RAB, PRODCOST, PKS, TRANSFER_REQUEST, BAST). `Entity` hanya terisi kalau `Document_Type = QUOTATION` (YKB atau PT KAI — lihat `Config.QUOTATION_ENTITIES`; satu project bisa punya 2 baris Quotation, satu per entitas), kosong untuk tipe lain. `Status` kosakatanya beda-beda per `Document_Type` (lihat `Config.DOCUMENT_STATUS_MAP`), sementara `Stage` selalu salah satu dari 4 nilai universal (`New Request`, `In Progress`, `Client Review`, `Done`) yang diturunkan otomatis dari `Status`. Aturan auto-advance ke `Project.Stage`: DECK/COR/RAB/PRODCOST — salah satu Done -> `Negotiation`; QUOTATION — begitu SEMUA Quotation yang diminta untuk project itu Done -> `Won` (Deal); PKS/TRANSFER_REQUEST/BAST adalah dokumen pasca-Deal yang TIDAK PERNAH memengaruhi Stage. Dokumen diminta lewat box "Document Request" di Project Detail (Sales Pipeline); KHUSUS COR ada pintu kedua, tombol "🧮 Buat COR" di halaman Document Pipeline (COR memang dikerjakan dari halaman itu) — keduanya memanggil backend yang sama. Lihat `DocumentService.checkAndAdvanceProjectStage`. Kolom `Document_Link` (link manual ke file dokumen ini) dan `Notes` (catatan bebas, berlaku untuk SEMUA Document_Type) sama-sama SELF-MIGRATING (ditambahkan otomatis oleh `DocumentPipelineRepository.ensureColumns` saat pertama kali dipakai) — tidak perlu diedit manual di sheet.

     **Dua kelonggaran khusus COR (`Config.DOCUMENT_REPEATABLE_TYPES` & `Config.DOCUMENT_PROJECTLESS_TYPES`) — tidak perlu perubahan sheet apa pun:**
     - Satu project boleh punya **lebih dari satu COR**, kapan saja, tanpa batas jumlah, dan tanpa perlu menunggu COR sebelumnya selesai. Sifatnya **KUMULATIF, bukan revisi**: COR baru TIDAK menggantikan COR lama, dan keduanya sama-sama ikut dijumlahkan di Dashboard (Implementation Fee) & Cost Monitoring. Tidak ada penomoran "tahap" — tiap COR dibedakan lewat `Doc_ID` dan tanggal permintaannya. Tipe dokumen LAIN tetap sekali per project seperti sebelumnya.
     - COR boleh dibuat **tanpa dikaitkan ke project mana pun** (`Project_ID` dibiarkan KOSONG di sheet). Alurnya sama persis — tetap lewat approval Head of B2B — yang berbeda hanya labelnya ("Tanpa Project" di tabel, drawer, PDF, dan subject email approval) dan folder PDF-nya jatuh ke `ROOT_FOLDER_ID` karena tidak ada folder project. Baris seperti ini SENGAJA tidak pernah menggerakkan Stage project mana pun. Hanya COR yang boleh begini; tipe lain tetap wajib punya project.
   > **Kalau sheet `Client` sudah pernah Anda buat sebelumnya**: tambahkan kolom baru `Other_Notes` (taruh di antara `Created_By` dan `Last_Updated`, atau di mana saja — asal namanya persis `Other_Notes`, urutan kolom tidak masalah karena kode membaca berdasarkan nama header, bukan posisi).
   - `COR_Entity` dengan header baris pertama: `Entity_ID | Entity_Name | Bank | Is_PKP | Biaya_Pencairan | Created_By | Created_Date`. Ini replika tabel `INDEX` di spreadsheet "Template COR" — daftar entitas/vendor (Salam Setara, PT BAA, dst) beserta bank, status PKP (TRUE/FALSE), dan biaya pencairan tetap (Rupiah). Dipakai dropdown "Via Vendor" di kalkulator COR (menyusul di tahap berikutnya). Isi baris awal sesuai tab INDEX Anda, contoh:
     ```
     Entity_ID | Entity_Name  | Bank    | Is_PKP | Biaya_Pencairan
     ENT-001   | Salam Setara | BSI     | FALSE  | 2500
     ENT-002   | PT BAA       | MANDIRI | FALSE  | 800
     ENT-003   | PT ABC       | BCA     | FALSE  | 1200
     ENT-004   | PT GDV       | BRI     | FALSE  | 900
     ```
   - `COR_Header` dengan header baris pertama: `Doc_ID | Cor_Method | Is_Via_Salset | Vendor_Entity | Ngo_Rate | Biaya_Salset | Is_Mix_Fund | Single_Fund_Type | Link_Campaigns | Output_File_Id_Client | Output_File_Id_Campaign | Created_By | Created_Date | Last_Updated`. Satu baris per dokumen COR (1:1 dengan `Doc_ID` di `Document_Pipeline`). `Cor_Method` salah satu dari `Config.COR_METHOD` (`GROSS_DOWN` atau `GROSS_UP` — admin pilih satu, tidak wajib dua-duanya). `Single_Fund_Type` (`CLIENT`/`CAMPAIGN`/kosong) hanya terisi untuk CARA 3 (Gross Down, bukan Via SALSET, bukan Mix Fund) — hasil dari wizard "Kerjakan COR" yang mengunci Source of Fund supaya cuma 1 jenis dana yang bisa diisi. `Link_Campaigns` string JSON array (murni informasi, tidak memengaruhi kalkulasi). `Output_File_Id_Client`/`Output_File_Id_Campaign` diisi otomatis setelah file Sheets di-generate (Campaign hanya terisi kalau `Is_Mix_Fund` true). Kosong untuk sekarang — akan dipakai mulai tahap generate file Sheets. `Manual_Project_Name` (self-migrating) — nama project manual, HANYA relevan & tersimpan untuk COR yang sengaja dibuat tanpa project (`Project_ID` kosong, lihat `Config.DOCUMENT_PROJECTLESS_TYPES`); diisi admin dari halaman Kalkulator COR, menggantikan label generik "Tanpa Project" di tabel Document Pipeline, PDF approval, dan Cost Monitoring. Dikosongkan otomatis oleh server untuk COR yang ternyata punya project (walau kebetulan terkirim dari klien). `Is_Salset_Only` (self-migrating, TRUE/FALSE) — COR "SALSET Saja": sama sekali tidak melalui Vendor. Kalau `TRUE`, server MEMAKSA `Is_Via_Salset = TRUE` juga (tidak dipercaya mentah dari klien), Kalkulator COR menyembunyikan seluruh box yang berkaitan dengan Vendor (Fund Detail, Default Margin, Biaya Pengeluaran SALSET/Vendor), dan dokumennya DIKELUARKAN TOTAL dari Cost Monitoring (bukan cuma tampil kosong) — lihat `CostMonitoringService.listForMonitoring`/`getDetail`. Dipilih lewat pertanyaan tambahan di wizard "Kerjakan COR" (setelah "Via SALSET? Ya") — bukan toggle bebas di kalkulator. `Margin_Enabled` (self-migrating, TRUE/FALSE, default TRUE), `Margin_Mode` (self-migrating, `COMPONENT`/`MANUAL`, default `COMPONENT`), dan `Manual_Margin_Pct` (self-migrating, angka, default 0) — toggle box "4. Default Margin" (Gross Down). `Margin_Enabled = FALSE` artinya TIDAK ADA profit yang diambil di muka: Available Cost Vendor = Cash In Vendor persis (tidak dipotong margin apa pun), tabel Default Margin di-skip di Kalkulator & PDF (diganti 1 baris catatan) — margin & profit AKTUAL (dari cost sungguhan) tetap kelihatan di box "Margin & Profit Margin" karena rumusnya independen dari toggle ini. Kalau `Margin_Enabled = TRUE`, `Margin_Mode` menentukan Total Margin dihitung dari 4 dropdown komponen (`COMPONENT`, perilaku lama) atau dari satu angka `Manual_Margin_Pct` yang diketik langsung (`MANUAL`, dropdown komponen diabaikan). Dokumen lama (kolom belum ada, `undefined`) selalu jatuh ke `Margin_Enabled=TRUE` + `Margin_Mode=COMPONENT` — perilaku sebelum toggle ini ada, sehingga COR yang sudah Approved tidak berubah angkanya. Hanya berlaku untuk `Cor_Method = GROSS_DOWN` (Gross Up tidak punya konsep "Cash In" di muka untuk dijadikan acuan langsung).
   - `COR_Fund` dengan header baris pertama: `Fund_ID | Doc_ID | Fund_Type | Link_Campaign | GDV | Platform_Fee | Tech_Fee | NDV | Disbursement_Fee | Implementation_Fund | Is_Zakat | Sort_Order`. Baris "Source of Fund" (dana masuk) — hanya relevan untuk `Cor_Method = GROSS_DOWN`. `Fund_Type` salah satu dari `Config.COR_FUND_TYPE` (`CLIENT`/`CAMPAIGN`). `GDV` (dulu bernama `Nominal` — **kalau sheet Anda masih pakai nama lama, rename manual header-nya jadi `GDV`**, datanya tidak perlu dipindah) adalah dana masuk mentah sebelum potongan apa pun; `Platform_Fee`/`Tech_Fee`/`NDV`/`Disbursement_Fee`/`Implementation_Fund` adalah HASIL hitungan (bukan input admin) yang dihitung ulang & disimpan otomatis oleh `CorService` setiap "Simpan Draft"/convert — kolom-kolom ini sendiri sudah self-migrating (ditambahkan otomatis kalau belum ada). `Campaign_Fund_Kind` (self-migrating juga) — sub-klasifikasi sumber Dana Campaign: `CAMPAIGN`/`DBT`/`FRAUD` (lihat `Config.COR_CAMPAIGN_FUND_KIND`), default `CAMPAIGN`, HANYA relevan untuk baris `Fund_Type = CAMPAIGN` (kosong untuk baris Dana Client) — murni label pelacakan, tidak memengaruhi kalkulasi apa pun. `Tech_Fee_Manual` (self-migrating, TRUE/FALSE, default FALSE) — HANYA relevan untuk `Fund_Type = CLIENT`: kalau `TRUE`, kolom `Tech_Fee` di baris itu BUKAN hasil hitungan 1% otomatis lagi, melainkan nilai yang diketik manual admin di Kalkulator COR (tombol pensil pada baris dana). Checkbox "Zakat/Bencana" (dulu "Zakat") hanya menolkan `Platform_Fee` — `Tech_Fee` TETAP terhitung (otomatis 1% ATAU manual, sesuai `Tech_Fee_Manual`) walau dana itu ditandai Zakat/Bencana.
   - `COR_Cost` dengan header baris pertama: `Cost_ID | Doc_ID | Cor_Tab | Cost_Group | Keterangan | Kategori | Tipe | Harga | Qty | Periode | Sort_Order`. Baris item biaya (tabel Cost SALSET/Cost Vendor), dipakai baik oleh Gross Down maupun Gross Up. `Cor_Tab` (`CLIENT`/`CAMPAIGN`) memisahkan baris kalau dokumen Mix Fund. `Cost_Group` salah satu dari `Config.COR_COST_GROUP` (`SAL`/`VENDOR`). **Empat kolom metode input cost (`Cost_Mode | Cost_Category | Category_Order | Row_Role`) ditambahkan OTOMATIS** (self-migrating, tidak perlu diedit manual) — ini yang membuat satu tabel cost bisa memakai 3 metode per kategori: `GROUPED` (tiap item punya Harga/Qty/Periode sendiri — perilaku lama, dan default untuk semua baris yang dibuat sebelum kolom ini ada), `STANDALONE_ITEM` (SATU nominal untuk seluruh kategori: satu baris ber-`Row_Role = PRICE` memegang angkanya, baris `Row_Role = ITEM` di bawahnya murni nama/rincian tanpa angka), dan `STANDALONE_NO_ITEM` (tepat satu baris berharga, `Cost_Category` sengaja dikosongkan karena metode ini tidak memakai nama kategori). Baris ber-`Row_Role = ITEM` TIDAK PERNAH ikut penjumlahan mana pun — tidak ke total cost, tidak ke Gross Up/Down, dan tidak ikut dibekukan ke `COR_Budget_Item` saat approval.
   - `COR_Margin` dengan header baris pertama: `Margin_ID | Doc_ID | Cor_Tab | Component | Sub_Category | Percentage`. Snapshot pilihan Default Margin (4 baris per `Cor_Tab`, satu per `Config.MARGIN_COMPONENTS`) pada saat dokumen COR disimpan — `Percentage` disimpan sebagai nilai tetap (bukan referensi ke `Margin_Guide`) supaya dokumen lama tidak berubah kalau `Margin_Guide` direvisi belakangan.
   - `COR_Result` (sheet BARU — **wajib dibuat manual**, header row TIDAK bisa self-migrate karena ini sheet baru bukan kolom baru) dengan header baris pertama persis: `Result_ID | Doc_ID | Cor_Tab | Total_Implementation_Fund | Salset_Gross | Salset_NGO_Fee | Gross_Vendor | PPN_Gross_Down | Pph_23_Vendor | Net_Vendor | Cost_Estimate_Vendor | Profit_Estimate_Vendor | Margin_Estimate_Vendor | Last_Updated`. Ledger hasil hitungan (bukan input mentah) rantai Gross Down — 1 baris per `Doc_ID` + `Cor_Tab` (2 baris kalau Mix Fund), direplace otomatis setiap "Simpan Draft"/convert untuk dokumen ber-`Cor_Method GROSS_DOWN`, jadi acuan dashboard tanpa perlu hitung ulang rumus COR. Kalau sheet ini belum dibuat, "Simpan Draft" tetap berhasil menyimpan data mentahnya (funds/costs/margins) — cuma ledger ini yang tertunda sampai sheet-nya ada.
   - `COR_Budget_Item` (sheet BARU — **wajib dibuat manual**) dengan header baris pertama persis: `Budget_Item_ID | Doc_ID | Cor_Tab | Cost_Group | Keterangan | Kategori | Budgeted_Amount | Sort_Order | Snapshot_At`.    - `Quotation_Header` dengan header baris pertama: `Doc_ID | Entity_Code | Language | Quotation_Number | Valid_Days | Valid_Date | Entity_Name | Pic_Client_Id | Pic_Name | Pic_Email | Pic_Phone | Head_Name | Title_Name | Service_Name | First_Statement | Important_Remarks | Agency_Fee_Rate | Pdf_File_Id | Pdf_File_Url | Created_By | Created_Date | Last_Updated`. Catatan: kolom yang belum ada di sheet akan ditambahkan OTOMATIS oleh `QuotationHeaderRepository` saat pertama kali dipakai, jadi kalau nanti ada field baru menyusul, sheet tidak perlu diedit manual.

Kolom yang belum ada di sheet (termasuk `Category_Mode` ini kalau sheet-nya dibuat sebelum field ini ada) ditambahkan OTOMATIS oleh `QuotationItemRepository`.

   > **`GDV_Controller` — SPREADSHEET TERPISAH, bukan tab di spreadsheet database utama di atas.** Fitur ini (Setting > GDV Controller) merekonsiliasi klaim GDV manual dengan data realisasi dari Tableau, dan sengaja disimpan di file Google Sheets yang BERBEDA supaya tidak bercampur dengan database operasional platform. Admin upload 2 CSV sekaligus tiap kali (Brand & Not-Brand — metode tarik datanya beda di Tableau, tapi headernya sama), datanya digabung jadi satu snapshot. Langkah manual:

Alasannya: export sumbernya datang **per klien** (satu file = satu `account_name`), jadi kalau tab ini ditimpa setiap upload, mengunggah data satu klien akan **menghapus data klien lain**. UI menampilkannya sebagai "belum ada data", bukan Rp0, karena Rp0 untuk dana yang bisa dicairkan adalah klaim yang salah dan bisa memicu keputusan pencairan yang keliru.

## Opsi B — Native Apps Script Editor (manual)

Repo Git berfungsi sebagai **source of truth & histori perubahan** — setelah edit di editor, salin balik perubahan ke sini agar tetap terlacak.

1. Buat Google Spreadsheet baru untuk database platform ini, lalu buka **Extensions > Apps Script** (jadi *container-bound script*).
2. Buat sheet `Employee`, `Lead`, `Inbound_Raw`, `Client`, `PIC_Client`, `Master_Data`, `Project`, dan `Document_Pipeline` seperti di Opsi A langkah 1.
3. Di Apps Script Editor:
   - Hapus file `Code.gs` default.
   - Buat file baru untuk setiap file di folder `src/` pada repo ini. **Nama file harus sama persis dengan path relatif dari folder `src/`** (tanpa ekstensi), misal file di repo `src/50_Presentation/html/Lead/LeadCapturingContent.html` harus dibuat dengan nama `50_Presentation/html/Lead/LeadCapturingContent` di editor (GAS mendukung `/` sebagai pseudo-folder). Ini wajib sama karena kode (`createTemplateFromFile`, `include`) memanggil file berdasarkan nama ini.
   - Untuk file `.gs`, pilih tipe "Script". Untuk file di folder `html/`, pilih tipe "HTML".
   - Salin isi setiap file dari `src/` ke file yang sesuai di editor.
4. Buka `00_Core/00_Config.gs` di editor, isi `SPREADSHEET_ID` dengan ID Spreadsheet Anda (bagian di URL antara `/d/` dan `/edit`).
5. Deploy sebagai Web App: **Deploy > New deployment > Web app**. Set "Execute as: Me", dan "Who has access" sesuai kebutuhan.

Setiap kali mengembangkan modul baru di editor: kembangkan & test langsung di script.google.com, lalu salin file yang berubah/ditambahkan ke `src/` di repo ini, lalu commit.
